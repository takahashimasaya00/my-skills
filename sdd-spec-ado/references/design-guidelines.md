# 設計レベル深掘りガイドライン (Design Level Guidelines)

本ガイドラインは、Azure DevOps のワークアイテム（PBI, Bug, Task）を実装に移す前に、クラス単位の微視的な実装ではなく**設計レベル（アーキテクチャ・データモデル・機能仕様）**で突き詰めるための指針である。

---

## 1. 「設計レベル」と「実装詳細」の明確な境界

### ✅ 設計レベル（Grilling & ドキュメント反映の対象）
- **システム構成 & 責務境界**:
  - どのコンポーネント（Angular SPA, NestJS API, Azure Functions, Cosmos DB, Azure Blob Storage 等）が何を担当するか。
  - 新規パッケージやモジュールが必要か、既存モジュールの拡張か。
- **データモデル & スキーマ**:
  - Cosmos DB ドキュメント構造、エンティティ定義、型（TypeScript interface / type）。
  - パーティションキー（Partition Key）、一意性制約、インデックス要件。
  - 他エンティティとのリレーション・参照方式（埋め込み vs 参照）。
- **API & 通信仕様**:
  - エンドポイント設計（パス、HTTPメソッド、クエリ/パスパラメータ）。
  - リクエストボディ / レスポンスボディのデータ構造（DTO）。
  - 認証・認可要件（ロール、ホワイトリスト等）。
- **UIステート & 画面フロー**:
  - 画面遷移、ユーザー操作に対する状態変化（Loading / Success / Empty / Error）。
  - `docs/design/` が存在する場合、デザインコンセプト（トーン＆マナー）やデザイントークンとの調和。
  - 全体機能マップ（`features.md` 内のMermaidダイアグラム）における位置づけ。
- **非機能要件 & 異常系**:
  - エラーハンドリング方針、タイムアウト・リトライ制御、冪等性。
  - レスポンス性能、同時実行制御（楽観的ロック等）。
- **技術選定 & アーキテクチャ決定 (ADR)**:
  - 複数の設計選択肢がある場合のトレードオフ比較と決定理由。

### ❌ 実装詳細（本スキルでは扱わない対象外）
- 単一関数やメソッドの内部コード、アルゴリズムの1行ごとの実装。
- ローカル変数名、内部ヘルパー関数の切り出し。
- CSSの個別プロパティ値（margin, padding, exact color code 等）。（※トークン定義や全体スタイリング方針は設計レベルで決定）
- ユニットテストのモック実装コード詳細（テスト観点・検証コマンドは設計対象）。

## 2. 既存ドキュメントとの整合性確認

設計を進める際、エージェントは必ず以下の既存仕様書を参照し、既存設計と矛盾が生じないか確認する。

1. **`docs/spec/system-architecture.md`**:
   - 既存のテックスタック、レイヤー構成、リポジトリ構成（npm workspaces）、共通規約。
2. **`docs/spec/data-models.md`**:
   - 既存のデータモデル（User, HealthCheckup, DailyDietary, DailyBodyComposition 等）のスキーマおよび型。
3. **`docs/spec/features.md`**:
   - 全体機能マップ（Mermaid図）および各機能（ポータル、健診管理、メトリクス詳細、設定等）の既存仕様。
4. **`docs/design/` 配下のデザイン仕様（存在する場合）**:
   - `docs/design/concept.md`: デザイン哲学、ペルソナ、ビジュアルテーマ、トーン＆マナー、レイアウト・インタラクション原則。
   - `docs/design/tokens.md`: カラースケール、タイポグラフィ、スペーシング、コンポーネント造形（Radius/Elevation）。
5. **`docs/adr/` 配下の既存ADR**:
   - 過去の意思決定（Cosmos DB採用、Azure OpenAI連携、Bicep管理、テスト方針等）。
6. **`CONTEXT.md`**:
   - プロジェクト固有のドメイン用語・ユビキタス言語。

## 3. 設計Grillingの着眼点チェックリスト

Grillingラウンドを展開する際は、以下の観点からフロンティア（未決事項）を洗い出す：

- [ ] **アーキテクチャ**: どのサービス・パッケージにロジックを配置するか？新規エンドポイントが必要か？
- [ ] **データ整合性**: データ永続化は必要か？Cosmos DBのどのコンテナに格納するか？パーティションキーは何にするか？
- [ ] **エラー・境界値**: 外部API障害、データ不整合、権限不足、入力バリデーションエラー時にどう振る舞うか？
- [ ] **UI/UX**: 状態遷移（読み込み中、0件表示、失敗再試行）のユーザー体験はどうあるべきか？
- [ ] **デザイン整合性**: `docs/design/` がある場合、デザインコンセプトやデザイントークンと矛盾していないか？
- [ ] **トレードオフ**: 代替案（Alternative A vs Alternative B）はあるか？ADRを起票すべき決定か？
- [ ] **実装手順（ロードマップ）**: 段階的に開発・検証を進めるための依存関係はどうなっているか？
