# スクラム開発リファインメント・ガイドライン (Definition of Ready)

本ドキュメントは、Azure DevOps アイテム（Feature, PBI, Bug）の要件をつき詰める際の「深掘り観点」と「完了基準（Definition of Ready）」を定義します。

---

## 1. 原則: 実装詳細への踏み込み禁止

このリファインメントの目的は、**「スクラムチームがスプリント計画で受け入れられる状態（DoRを満たす状態）」** にすることです。

### 扱う内容（Why & What）
- 誰が・なぜこの機能を必要としているのか（ビジネス価値・ユーザー課題）
- どのような入出力・振る舞い・画面導線になるか
- どのような条件が満たされれば完成（Done/Accept）と判断できるか（受入基準）
- スコープの境界（何を含め、何を今回やらないか）
- 非機能要件の前提（性能要件、セキュリティ要件、監査要件などの方針）

### 扱わない内容（How - 実装詳細）
- クラス設計、関数名、ディレクトリ構成
- DBテーブルスキーマの物理カラム定義やインデックス設計
- 具体的なRESTエンドポイントURLや内部コードの実装
※ これらはスプリント期間中に開発者がタスク（Task）化して決める領域であるため、質問や成果物には含めないこと。

---

## 2. アイテム種別ごとの深掘り観点 & Definition of Ready (DoR)

### A. Feature
- **目的**: 複数のPBIを束ねるビジネス機能・価値の定義
- **DoRチェックリスト**:
  1. [ ] 解決するユーザー課題とビジネス価値（KPI/成功指標）が明確か？
  2. [ ] ターゲットユーザー（ペルソナ）が定義されているか？
  3. [ ] MVP（Phase 1）と将来スコープ（Phase 2以降）の境界が引かれているか？
  4. [ ] 独立してスプリントで消化可能な PBI（3〜6個程度）への分割案が揃っているか？
  5. [ ] 機能全体の受入基準（Feature Acceptance Criteria）が定義されているか？

### B. Product Backlog Item (PBI / User Story)
- **目的**: 1スプリント内で完結し、ユーザーに価値を届ける最小単位
- **DoRチェックリスト**:
  1. [ ] **ユーザーストーリー形式**で記述されているか？
        (`As a <ユーザー種別>, I want <機能/振る舞い>, So that <得られる価値/理由>`)
  2. [ ] **受入基準 (Acceptance Criteria)** が Given-When-Then 形式、または検証可能なチェックリストで曖昧さなく書かれているか？
  3. [ ] エッジケース（エラー時、データ0件時、異常入力時）の振る舞いが定義されているか？
  4. [ ] 前提条件・スコープ外（Out of Scope）が明記されているか？
  5. [ ] 見積もり可能なサイズ（1スプリントで開発〜テストが完了可能）になっているか？

### C. Bug
- **目的**: 障害や不具合の事象・期待動作を明確にし、修正の完了を判定可能にする
- **DoRチェックリスト**:
  1. [ ] 発生環境（ブラウザ、OS、アカウント権限など）が特定されているか？
  2. [ ] 再現手順（Step-by-step）が明確か？
  3. [ ] 「実際の動作（Actual）」と「期待される動作（Expected）」の差異が明確か？
  4. [ ] 影響度・緊急度（全ユーザーか特定条件か、データ損失や業務停止があるか）が整理されているか？
  5. [ ] 修正後の受入基準（何をどうテストすればBug解決と認めるか）が定義されているか？

## 3. 受入基準 (Acceptance Criteria) の記述フォーマット

受入基準は可能な限り **Given-When-Then**（Gherkin風）または明確なチェックリストを使用します。

#### 例: Given-When-Then 形式
```gherkin
Scenario: 有効なメールアドレスで登録
  Given ユーザーがサインアップ画面を開いている
  When 有効なメールアドレスとパスワードを入力して「登録」をクリックする
  Then 確認メールが送信され、完了画面が表示される

Scenario: 既に登録済みのメールアドレスの場合
  Given メールアドレス "test@example.com" が既に登録されている
  When 同一のメールアドレスで登録を試みる
  Then 「このメールアドレスは既に登録されています」というエラーメッセージが表示される
```

#### 例: 検証チェックリスト形式
- [ ] 正常系: 必須項目を全て入力した場合、2秒以内に登録が完了し一覧画面へ遷移する
- [ ] 異常系: 必須項目が未入力の場合、対象項目の下に赤字でエラーが表示される
- [ ] 権限: 管理者権限を持つユーザーのみが「削除」ボタンを押下できる
